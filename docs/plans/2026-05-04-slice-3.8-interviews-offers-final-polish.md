# Slice 3.8 - Interviews + Offers + Final Day 3 Polish Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (in the executing session) to implement this plan task-by-task. Dispatch a fresh subagent per task; review between tasks; halt on failure. **This is the last feature slice before deployment.** It closes the hire-flow loop - until now the application lifecycle stops at "applied → screening → interview → offer → hired" but the system has no UI for actually scheduling those interviews or sending those offers. This slice ships both. It's also the final polish gate for Day 3: every admin surface gets a quick mobile spot-check; lint must be green; the Day 3 EOD checklist must be all-green before Day 4 deployment work begins.

**Goal:** Three concerns in one slice (75-min budget; pace yourself):

1. **Ship `InterviewsModule`** - backend CRUD + frontend "Schedule interview" modal on `/recruiter/applications/[id]` + interview list pages for both candidate and recruiter portals + transactional emails (`interview-scheduled`, `interview-cancelled`).

2. **Ship `OffersModule`** - backend CRUD + frontend "Send offer" wizard at `/recruiter/offers/new?applicationId=...` + candidate-side Accept/Decline buttons on the offer detail surface + transactional emails (`offer-sent`, `offer-decision`).

3. **Day 3 final polish pass** - sweep new + existing surfaces for mobile breakpoints, ensure `pnpm lint` is zero-warnings clean, verify the Day 3 End-of-Day checklist (sprint-plan.md line 414-421) is all-green before handing off to Day 4 deployment slices.

**Architecture:** Two new modules under `apps/api/src/modules/` - `interviews/` and `offers/` - each with the standard controller/service/repository/dto/module layout (mirrors 2.6's ApplicationsModule structure). Both modules import `ApplicationsModule` (for ownership-check via `applicationsRepo.findApplicationContextForRecruiter`), `JobsModule` (for job lookup in email composition), `ProfilesModule` (for candidate/recruiter profile joins), and `EmailModule`. **Application status auto-transitions are minimal**: only `offer.accept` auto-advances `application.status → 'hired'` (the natural conclusion). Interview creation does NOT auto-advance from screening to interview - recruiter manually progresses status via 2.6's existing PATCH endpoint. This keeps state machine logic concentrated in one place (ApplicationsService) rather than scattered across feature modules.

**Tech Stack:** NestJS module/service/repo pattern (same as 2.6's ApplicationsModule), Drizzle for `interviewsTable` + `offersTable` writes, React Email for 4 new templates (interview-scheduled, interview-cancelled, offer-sent, offer-decision), reused `EmailService` from 1.5 (Mailpit dev / Resend prod), reused state machine guards from 2.6's `state-machine.ts` (offer accept calls `ApplicationsService.updateStatus(...)` with `newStatus: 'hired'`).

```ts
import { Inject, Injectable } from "@nestjs/common";
import { and, desc, eq } from "drizzle-orm";
import {
  applicationsTable,
  interviewsTable,
  jobsTable,
  type Interview,
  type NewInterview,
} from "@aurahire/db";

import { DRIZZLE_CLIENT, type DrizzleClient } from "../../db/db.module";

@Injectable()
export class InterviewsRepository {
  constructor(@Inject(DRIZZLE_CLIENT) private readonly db: DrizzleClient) {}

  async insert(data: NewInterview): Promise<Interview> {
    const [row] = await this.db
      .insert(interviewsTable)
      .values(data)
      .returning();
    if (!row) throw new Error("Interview insert failed");
    return row;
  }

  async findById(id: string): Promise<Interview | null> {
    const [row] = await this.db
      .select()
      .from(interviewsTable)
      .where(eq(interviewsTable.id, id))
      .limit(1);
    return row ?? null;
  }

  async findByApplicationId(applicationId: string): Promise<Interview[]> {
    return this.db
      .select()
      .from(interviewsTable)
      .where(eq(interviewsTable.applicationId, applicationId))
      .orderBy(desc(interviewsTable.scheduledAt));
  }

  async findByCandidateId(candidateId: string): Promise<Interview[]> {
    return this.db
      .select({ interview: interviewsTable })
      .from(interviewsTable)
      .innerJoin(
        applicationsTable,
        eq(applicationsTable.id, interviewsTable.applicationId),
      )
      .where(eq(applicationsTable.candidateId, candidateId))
      .orderBy(desc(interviewsTable.scheduledAt))
      .then((rows) => rows.map((r) => r.interview));
  }

  async findByRecruiterId(recruiterId: string): Promise<Interview[]> {
    return this.db
      .select({ interview: interviewsTable })
      .from(interviewsTable)
      .innerJoin(
        applicationsTable,
        eq(applicationsTable.id, interviewsTable.applicationId),
      )
      .innerJoin(jobsTable, eq(jobsTable.id, applicationsTable.jobId))
      .where(eq(jobsTable.recruiterId, recruiterId))
      .orderBy(desc(interviewsTable.scheduledAt))
      .then((rows) => rows.map((r) => r.interview));
  }

  async update(id: string, patch: Partial<NewInterview>): Promise<Interview> {
    const [row] = await this.db
      .update(interviewsTable)
      .set({ ...patch, updatedAt: new Date() })
      .where(eq(interviewsTable.id, id))
      .returning();
    if (!row) throw new Error("Interview update failed");
    return row;
  }
```

```ts
import {
```

```ts
  type NewOffer,

import { DRIZZLE_CLIENT, type DrizzleClient } from "../../db/db.module";

@Injectable()
export class OffersRepository {

  async insert(data: NewOffer): Promise<Offer> {
    const [row] = await this.db.insert(offersTable).values(data).returning();
    if (!row) throw new Error("Offer insert failed");
    return row;
  }

  async findById(id: string): Promise<Offer | null> {
    const [row] = await this.db
      .select()
      .from(offersTable)
      .where(eq(offersTable.id, id))
      .limit(1);
    return row ?? null;
  }

  async findByApplicationId(applicationId: string): Promise<Offer[]> {
    return this.db
      .select()
      .from(offersTable)
      .where(eq(offersTable.applicationId, applicationId))
      .orderBy(desc(offersTable.sentAt));
  }

  async findPendingByApplicationId(
    applicationId: string,
  ): Promise<Offer | null> {
    const [row] = await this.db
      .select()
      .from(offersTable)
      .where(
        and(
          eq(offersTable.applicationId, applicationId),
          eq(offersTable.status, "pending"),
        ),
      )
      .limit(1);
    return row ?? null;
  }

  async findByCandidateId(candidateId: string): Promise<Offer[]> {
    return this.db
      .select({ offer: offersTable })
      .from(offersTable)
      .innerJoin(
        applicationsTable,
        eq(applicationsTable.id, offersTable.applicationId),
      )
      .where(eq(applicationsTable.candidateId, candidateId))
      .orderBy(desc(offersTable.sentAt))
      .then((rows) => rows.map((r) => r.offer));

    const [row] = await this.db
      .update(offersTable)

      .returning();
```

```tsx
"use client";

import { useState } from "react";
import { useRouter } from "next/navigation";
import { toast } from "sonner";
import {
  Dialog,
  DialogContent,
  DialogFooter,
  DialogHeader,
  DialogTitle,
} from "@/components/ui/dialog";
import { Button } from "@/components/ui/button";
import { Textarea } from "@/components/ui/textarea";
import { createSupabaseBrowserClient } from "@/lib/auth/client";

interface OfferRow {
  id: string;
  status: string;
  title: string;
  salary: number;
  salaryCurrency: string;
  startDate: string;
  expiresAt: string | null;
}

export function OfferActionsClient({ offer }: { offer: OfferRow }) {
  const router = useRouter();
  const [working, setWorking] = useState(false);
  const [declineOpen, setDeclineOpen] = useState(false);
  const [reason, setReason] = useState("");

  async function authedPost(path: string, body?: object) {
    const supabase = createSupabaseBrowserClient();
    const {
      data: { session },
    } = await supabase.auth.getSession();
    if (!session) throw new Error("Not signed in");
    const apiUrl = process.env.NEXT_PUBLIC_API_URL ?? "http://localhost:3333";
    return fetch(`${apiUrl}${path}`, {
      method: "POST",
      headers: {
        Authorization: `Bearer ${session.access_token}`,
        "Content-Type": "application/json",
      },
      body: body ? JSON.stringify(body) : undefined,
    });
  }

  async function accept() {
    if (
      !window.confirm(
        "Accept this offer? Your application status will move to 'hired'.",
      )
    )
      return;
    setWorking(true);
    try {
      const res = await authedPost(`/api/v1/offers/${offer.id}/accept`);
      if (!res.ok) {
        toast.error("Accept failed");
        return;
      }
      toast.success("Offer accepted! Welcome aboard.");
      router.refresh();
    } finally {
      setWorking(false);
    }
  }

  async function decline() {
    setWorking(true);
    try {
      const res = await authedPost(`/api/v1/offers/${offer.id}/decline`, {
        reason: reason || null,
      });
      if (!res.ok) {
        toast.error("Decline failed");
        return;
      }
      toast.success("Offer declined");
      setDeclineOpen(false);
      router.refresh();
    } finally {
      setWorking(false);
    }
  }

  if (offer.status !== "pending") {
    return (
      <p className="text-sm text-[var(--color-muted)]">
        This offer is <strong>{offer.status}</strong>.
      </p>
    );
  }

  return (
    <>
      <div className="flex flex-wrap gap-2">
        <Button
          onClick={accept}
          disabled={working}
          className="rounded-[var(--radius-pill)] bg-[var(--color-score-high)] hover:opacity-90"
        >
          Accept Offer
        </Button>
        <Button
          onClick={() => setDeclineOpen(true)}
          disabled={working}
          variant="outline"
          className="rounded-[var(--radius-pill)]"
        >
          Decline
        </Button>
      </div>

      <Dialog open={declineOpen} onOpenChange={setDeclineOpen}>
        <DialogContent>
          <DialogHeader>
            <DialogTitle>Decline this offer?</DialogTitle>
          </DialogHeader>
          <p className="text-sm text-[var(--color-body)]">
            Optional: tell the recruiter why (helps them improve).
          </p>
          <Textarea
            value={reason}
            onChange={(e) => setReason(e.target.value)}
            rows={3}
            placeholder="e.g., accepted another offer, role wasn't the right fit..."
          />
          <DialogFooter>
            <Button
              variant="outline"
              onClick={() => setDeclineOpen(false)}
              className="rounded-[var(--radius-pill)]"
            >
              Cancel
            </Button>
            <Button
              onClick={decline}
              disabled={working}
              className="rounded-[var(--radius-pill)] bg-[var(--color-status-danger)]"
            >
              Confirm decline
            </Button>
          </DialogFooter>
        </DialogContent>
      </Dialog>
    </>
  );
}
```

## Why This Slice Matters

This slice closes the **hire-flow loop**. Until now, the application lifecycle stops at "applied → screening → interview → offer → hired" but the system has had no UI for actually scheduling those interviews or sending those offers - recruiters could PATCH status manually but couldn't capture the structured artifacts (when is the interview, what's the salary, what's the start date). After this slice:

1. **The thesis demo plays end-to-end.** Maria applies → recruiter schedules an interview → candidate accepts → recruiter sends an offer → candidate accepts → application status auto-advances to 'hired'. **The full hire arc, in 5 minutes of demo time.**

2. **The audit trail completes.** Every step in the arc - interview scheduled, status changed, offer sent, offer accepted, application advanced to hired - writes to `audit_logs`. Examiners can query `WHERE entity_id IN (applicationId, interviewId, offerId)` and see the full provenance of a hire from first apply to acceptance.

3. **The candidate portal has its bookend.** Until this slice, the candidate's view of an application was "you applied N days ago, here's your match score, status is X." After this slice, the candidate gets the moment that matters most - Accept Offer button, with consequences (auto-advance to hired). That's the journey the system was built to support.

The 75-minute budget is real but tight. The risk is scope creep - there's a temptation to add interview reminder emails, calendar integrations, offer templating, salary benchmarking. **All of those are Phase 4+.** This slice's job is the minimum viable hire arc + final Day 3 polish, so Day 4 starts on time with deployment work, not bug fixes.

After 3.8: Day 3 is a wrap. The application is feature-complete. Day 4 is purely deployment + smoke test + docs pass.
